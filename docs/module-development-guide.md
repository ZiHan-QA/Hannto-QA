# Hannto QA 管理平台模块开发与迁移规范

## 1. 目的

本规范用于多人共同开发 Hannto QA 管理平台，以及将外部模块迁移到本平台。目标是保证模块可以独立开发，同时统一项目、用户、权限、数据、交互和发布流程。

适用范围：

- 新增业务模块；
- 将其他系统的页面或数据迁入本平台；
- 修改公共导航、权限、项目、版本和工作事项能力；
- 新增 Supabase 表、函数、Edge Function 或外部服务同步。

## 2. 当前架构与迁移原则

当前平台是 GitHub Pages 静态站点，主要业务仍集中在 `main.html`。多人开发时禁止继续把大段新功能直接堆入该文件。

采用渐进式模块化：

1. 先提取无副作用的配置、公共工具和样式；
2. 再迁移低耦合模块；
3. 每次只迁移一个模块，并保持现有入口可用；
4. 每次迁移后完成本地验收，再开始下一模块；
5. 工作事项和项目总排期最后迁移，因为两者数据依赖最多。

禁止一次性重写整个平台。

## 3. 推荐目录

```text
src/
  core/                  # 平台初始化、路由、权限、模块注册
  shared/                # 公共组件、工具和样式
  modules/
    departments/
    feedback/
    projects/
    releases/
    reports/
    tasks/
    portfolio/
docs/
supabase/
  migrations/
scripts/
```

模块不得复制 Supabase 客户端、登录逻辑、项目分类、用户职责或消息提示实现。

## 4. 模块契约

每个模块必须声明：

```js
HanntoQA.registerModule({
  id: 'feedback',
  title: '意见反馈',
  owner: '开发负责人',
  version: '1.0.0',
  projectAware: true,
  permissions: ['admin', 'qa_lead', 'tester'],
  render: async context => {},
  destroy: () => {},
});
```

约束：

- `id` 全局唯一，只允许小写字母、数字和短横线；
- `render` 必须处理加载、空数据、失败和无权限状态；
- 注册阶段不得发请求、操作 DOM 或订阅 Realtime；
- Realtime、事件监听器和定时器必须在 `destroy` 中清理；
- 重复进入页面不得产生重复订阅或重复监听；
- 模块不得修改其他模块的内部状态。

## 5. 项目与数据关联

项目管理模块中的业务数据必须尽可能关联：

| 字段 | 说明 |
|---|---|
| `business_unit` | `xiaomi`、`consumer`、`other` |
| `project_id` | `qa_projects.id` |
| `release_id` | 关联版本，可为空 |
| `created_by` | 创建用户 UUID |
| `updated_by` | 最近修改用户 UUID |
| `created_at` | 数据库生成的创建时间 |
| `updated_at` | 数据库生成的更新时间 |

规则：

- 不使用项目名称、成员姓名或邮箱作为稳定关联键；
- 项目、成员、版本和外部对象均使用 UUID 或稳定外部 ID；
- “小米 / 消费 / Other”切换必须真实过滤查询结果，不能只改变按钮样式；
- 未关联项目的数据必须进入“待归属”队列，不能静默遗漏；
- 删除项目默认采用归档，硬删除仅限系统管理员并需要二次确认。

## 6. 身份、职责与权限

平台统一使用三种职责：

| 职责 | 代码值 | 主要权限 |
|---|---|---|
| 系统管理员 | `admin` | 系统设置、职责、删除和全部数据 |
| QA负责人/项目负责人 | `qa_lead` | 项目、成员、排期、版本和团队质量数据 |
| 测试工程师 | `tester` | 参与项目和本人工作事项 |

要求：

- 模块不得维护自己的管理员名单；
- 前端隐藏按钮只负责体验，数据库 RLS 才是真正授权；
- 所有新增表必须启用 RLS；
- `SELECT`、`INSERT`、`UPDATE`、`DELETE` 分别评估，禁止直接授予匿名角色写权限；
- 服务端从会话读取操作者身份，不能信任浏览器提交的用户名或角色；
- 负责人多选使用关联表，不用逗号分隔文本。

## 7. Supabase 数据库迁移

迁移文件命名：

```text
supabase/migrations/YYYYMMDD_description.sql
```

规则：

- 已执行的历史迁移文件不得修改；
- 生产库禁止只在控制台手工改表而不提交 SQL；
- 新表必须包含主键、必要外键、索引、时间字段、RLS 和策略；
- 外键删除行为必须明确使用 `RESTRICT`、`SET NULL` 或 `CASCADE`；
- 大表新增索引、约束和字段要评估锁表时间；
- 删除表、列、策略或数据必须单独 PR，并提供回滚和影响说明；
- 迁移尽可能使用 `if exists` / `if not exists`；
- SQL 执行后保存验证查询结果；
- Schema 变更后刷新 Supabase Schema Cache。

迁移 PR 必须说明：

1. 新增或修改的对象；
2. 现有数据如何处理；
3. RLS 权限矩阵；
4. 执行顺序；
5. 回滚方式；
6. 是否可能锁表。

## 8. 外部服务与密钥

前端只允许公开的 Supabase `anon key`。以下内容禁止写入 Git、页面、日志或数据库普通字段：

- Hanntonb / PingCode API Key；
- Supabase service role key；
- 用户密码；
- 管理员令牌；
- Edge Function Secret。

PingCode 和 TestHub 调用必须经过受控服务端、Supabase Edge Function 或批准的本地同步工具。写回必须：

- 由已登录用户显式触发；
- 使用幂等键避免重复创建；
- 保存动作、操作者、外部 ID、结果和错误摘要；
- 失败时保留本地数据；
- 批量操作前展示新增、更新和跳过数量。

## 9. 状态、日期和人力口径

工作事项状态统一为：

```text
todo / in_progress / blocked / done / cancelled
```

页面负责显示中文，数据库保存固定代码值。

时间规则：

- 业务时区统一为 `Asia/Shanghai`；
- 时间戳使用带时区类型；
- 纯日期使用 `YYYY-MM-DD`；
- 可信完成时间以数据库服务器时间为准；
- 人力排期支持上午、下午和全天；
- 已完成事项仍保留历史排期与资源占用；
- 周末和节假日使用统一工作日历。

## 10. 页面与交互要求

每个模块必须具备：

- 加载状态；
- 空数据状态；
- 请求失败与重试入口；
- 无权限状态；
- 保存中状态；
- 防重复提交；
- 成功或失败反馈；
- 弹窗打开时禁止点击蒙层返回；
- 窄屏基础适配。

数据源缺失时显示“暂无数据”或“待配置”，禁止用 `0` 冒充真实结果。单个接口失败不能阻止其他区域显示。

## 11. Git 与 PR 规则

- 禁止直接向 `main` 推送；
- 分支使用 `codex/` 或团队约定前缀；
- 一个 PR 只处理一个模块或一个明确问题；
- 公共核心文件修改必须单独说明影响范围；
- 不在功能 PR 中格式化整个大文件；
- 合并前同步最新主分支并解决冲突；
- PR 必须附本地验证结果和必要截图；
- SQL、前端和权限变化必须在 PR 描述中分别列出；
- 不得覆盖其他开发者尚未合并的改动。

## 12. 模块迁移交付清单

迁移负责人必须提供：

- 模块名称、负责人和范围；
- 原系统入口；
- 新平台入口；
- 项目、版本和工作事项关联方式；
- 使用或新增的数据表；
- 三种职责的权限矩阵；
- 外部 API 和密钥使用方式；
- 历史数据迁移与去重方案；
- SQL 迁移文件；
- 加载、空数据、失败和无权限截图；
- 验收步骤；
- 回滚方式；
- 已知限制。

## 13. 合并验收底线

合并前必须确认：

- 项目分类真实过滤数据；
- 普通成员不能越权访问或修改；
- 所有新增写操作受 RLS 保护；
- 无硬编码服务端密钥；
- 重复点击不会创建重复数据；
- 事件监听和 Realtime 不会重复订阅；
- 单个请求失败不会拖垮整页；
- 数据库迁移在目标环境执行成功；
- `python scripts/self_check.py` 通过；
- `git diff --check` 通过；
- 本地页面实际打开并完成主要操作；
- 管理员、QA 负责人、测试工程师分别验收权限。

## 14. 推荐迁移顺序

当前实际状态和交接要求见
[`developer-handoff-current-state.md`](./developer-handoff-current-state.md)。

后续推荐顺序：

1. ~~公共配置、模块注册和 BU 配置~~（已建立基础能力）；
2. ~~意见反馈~~（已完成）；
3. ~~项目总览~~（已完成）；
4. 工作事项第二阶段（入口、查询、列表和详情已迁移）；
5. ~~版本与发布~~（已完成）；
6. 质量报表第八阶段（查询、筛选、指标、任务/BUG 明细视图模型、成员分摊、复盘与对外简报统计、周简报分组已迁移）；
7. 项目总排期；
8. BUG 管理；
9. 账号与权限；
10. 工作台；
11. 统一 UI、性能和自动化回归优化。
